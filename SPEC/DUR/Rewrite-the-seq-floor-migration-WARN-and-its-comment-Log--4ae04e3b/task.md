## Description

The seq-floor migration WARN in internal/hub/hub.go (the `migrating` branch, reached when hub.Open backfills message-seq-floor from a derived, non-zero floor on a data directory that predates the file) previously ended: "...this start verified that recovery removed no records from that log, so this start closes the window". Literally true (recovery discarded nothing) and substantively FALSE: a truncation landing EXACTLY ON A RECORD BOUNDARY removes records from the log without leaving anything torn for recovery to discard, so the guard the WARN is describing (o.LogRepaired) cannot see it and the WARN told the operator the window was closed at precisely the offsets where it was open.

This task is CLOSING A FALSE STATEMENT, not the underlying hole. The guard (o.LogRepaired) is still blind at 100% of record boundaries -- measured on a real specimen, exhaustively swept (8900 offsets, both halves): every non-boundary offset REFUSED loudly, and every one of 22 record-boundary offsets escaped the guard, 13 of them reissuing an already-delivered sequence (one reissuing a message id end to end). That is a property of the code, not a rare corner case, and this task does not change it. The durability area (message sequence floor / migration window) is NOT cleared by this task -- it stays open, tracked as Spec Server task 9fd58deb (the consumed-index field that would actually close the hole) and its blocked follow-up. Do not let anyone read this task as though the reissue path is fixed.

WHAT LANDED: rewrote the WARN log line, its surrounding comment block, and the Options.LogRepaired field doc comment to claim only the discard check that ran ("recovery discarded no records") and explicitly name the boundary-truncation blind spot the check cannot see, with an "UNPROVEN FLOOR:" prefix so the caveat survives truncation by downstream log pipelines (the message is kept under the 1024-byte logging cap). Added TestSeqFloorMigrationWarningDoesNotClaimTheLogIsComplete (internal/hub/mint_test.go), which pins the banned old phrasing absent and the new honest phrasing present, and asserts the message is not truncated by the logging cap.

Scope: text-only (WARN message, its comment, the LogRepaired field doc, and the new test). The predicate (o.LogRepaired), the refusal guard (ErrSeqFloorUnprovable) and the WARN/ERROR level split were NOT touched.

Both reviewer and security gates ran on this change and independently confirmed no existing task owned it (be447589 is done, the data-dir-permissions task; 9fd58deb is the still-open/blocked tracking task for the actual fix) -- both returned PASS. This task exists to record those two verdicts in the journal, since the change landed without an owning task.
