```
=== RUN   TestInviteNotDurableIsRefused
    store_test.go:1531: Lookup on a store with no durable log did not find the replayed record
--- FAIL: TestInviteNotDurableIsRefused (0.00s)
```

ROOT CAUSE (pinned, not guessed): internal/invite/store_test.go newReplayFixture (:1140-1151) hardcodes `base := time.Date(2026, 8, 7, 12, 0, 0, 0, time.UTC)` and builds the open fixture record with `ExpiresAt: base.Add(24 * time.Hour)` -- i.e. 2026-08-08T12:00:00Z, fixed at authoring time. TestInviteNotDurableIsRefused builds its store via `invite.NewStore(invite.StoreOptions{BusID: testBusID})` with NO `Now` override, so `s.now` defaults to the REAL `time.Now` (store.go:181-183). `Lookup` calls `sweepLocked(s.now())` before returning (store.go:356-365, :1073-1087), and `sweepLocked` deletes any open record once `now.After(retiredAt(r))`, where for an open record `retiredAt = ExpiresAt + SpentRetention` (store.go:1103-1113) and `SpentRetention` defaults to `idem.RetentionWindow` (~50h10m22s, internal/idem/retention.go:78). That puts the fixtures retirement at 2026-08-10T14:10:22Z. Verified arithmetically: current wall-clock date is already several days past that instant, so the fixture record is durably swept out of the table by the time `Apply` (line 1527) hands it to `Lookup` (line 1530) -- the test asserts a record is present that its own fixture guarantees will already be gone, once real time crosses the baked-in threshold.

This is NOT a logic bug in internal/invite -- Apply/upsertLocked/sweepLocked/Lookup all behave exactly as documented; SpentRetention sweeping expired records is the intended, tested behaviour. The bug is entirely in the TEST: a fixture using a hardcoded past date against a store built with the real wall clock is a time bomb that was guaranteed to start failing once enough real time passed, and nothing pinned the clock to prevent that.

FIX: give TestInviteNotDurableIsRefused (and audit newReplayFixture/committedRecord for other callers with the same shape) an injected `Now` via `StoreOptions.Now` that stays fixed relative to `base`, exactly like the stores other durability/monotonicity tests presumably already do elsewhere in this file -- so the Lookup-after-Apply assertion is about REPLAY correctness, not about how much wall-clock time has elapsed since the test was written. Do not simply push `base` further into the future: that only delays the same failure, it does not fix the underlying time-bomb pattern. Grep the whole invite test suite for other `time.Date(2026,` literals used with a NewStore call that has no `Now:` override, since the same pattern could be latent elsewhere and this is the second time-bomb class found in this repo family (see CLAUDE.md guidance on verifying against a clean HEAD overlay).

Why this matters beyond one test (stated by the requester and worth keeping in the record): every agent in this repo verifies against a clean-HEAD overlay before trusting its own change; a red test at HEAD makes every one of those verifications noisier and trains people to attribute failures to their own diff when the failure is actually pre-existing and unrelated.
