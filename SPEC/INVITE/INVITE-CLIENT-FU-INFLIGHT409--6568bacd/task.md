## Description

DISCOVERED BY: reviewer/security gate during INVITE-CLIENT (4123e25d-4644-48e0-9ee1-e0a9a273fd8c)

The bus answers `invite.ErrRedemptionInFlight` with `409 "another redemption of this invite is in flight; retry"` -- a TRANSIENT condition whose correct remedy is to retry. The client instead reports "an idempotency key was reused with different content; use a fresh key for new content (invariant 10)", which CONTRADICTS the bus, and a fresh key against a SINGLE-USE invite is the one action that turns a transient failure into a permanently lost enrolment. Worse: `KindRejected` falls into `client/enrol.go` `enrolFailed`'s default branch, so `DropPending` fires and DESTROYS the private key seed of an attempt that may already have been applied. Reviewer observed this against a stub returning the bus's real 409 body (`pending found=false`). Newly reachable -- before INVITE-CLIENT the client could not present an invite at all. Window is bounded (`internal/auth/service.go:463` releases the reservation on every exit, `ReservationTTL` 30s), which is why it is a follow-up rather than a blocker. Fix: distinguish the in-flight 409 from the key-reuse 409 and do NOT drop pending state on it.
