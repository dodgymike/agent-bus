## Description

cmd/agent-bus/invite.go:599 opens the log with Applier: store -- a bare *invite.Store. invite.Store.Apply skips any entry whose kind is not invite.RecordKind, and an invited enrolment is written as the COMPOSITE kind "agent+invite" (auth.EnrolInviteRecordKind), so every invite spent through the new redemption path is INVISIBLE to that wiring and rebuilds as OPEN. Bounded today because mint only appends -- what it currently gets wrong is Store.Len(), so the MaxInvites capacity check under-counts. It becomes an OPERATOR-FACING FALSE CLAIM the moment INVITE-REVOKE or an invite list subcommand lands on that wiring: an operator would be told a spent invite is still live, and could not revoke what the table says is open. Fix: build the same auth.NewMultiplexApplier over roster + store there, as cmd/agent-bus/main.go now does. NOTE the same trap is baked into the existing test helper cmd/agent-bus/invite_test.go:639 replayInvites. Found INDEPENDENTLY by the test-engineer and the security gate on 2026-08-14.
