## Description

Raised by the security gate on MTLS-CROSSCHECK as a MEDIUM, and it is a consequence that task CREATES rather than an unfinished improvement -- before it, an expired client certificate was harmless because nothing authorised on one. Now: WithClientCertificate attaches NOTHING for an out-of-date leaf (internal/httpapi/clientcert.go), so guard B refuses EVERY route including POST /v1/session/begin, meaning the agent cannot even obtain a session to ask for help. Client certificates are minted for 365 days and renewal is NOT automatic (client/clientcert.go:99-100, :210-211); CertBinding.RetiredAt is set by NO code path; no rebind/rotate route exists. The only remedy today is re-enrolment, which mints a NEW agent id (invariant 1 -- ids are never reused), losing the identity and its mailbox. This is NOT a reason to admit an expired certificate: expiry is the only automatic bound on a leaked client key, and RELAY-20 closed the identical hole on the peer plane. It is a reason to ship the retire/rebind route. Related existing task: 7a197025. Must land before any deployment binds certificates it cannot rotate. Note invariant 11 also requires rotation to serve TWO certificates during rollover WITHOUT re-enrolment, which the current shape supports on the read side (any live binding is accepted, not the newest) but has no write path for.
