## Description

MTLS-BIND shipped the cert->agent binding as CODE ONLY. Its file boundary made CONTRACTS-*.md, DECISIONS.md and AGENT_LOG.md OFF-LIMITS (several agents append to those concurrently), so the documentation half is owed and is tracked here. Raised as a blocker by the reviewer gate on MTLS-BIND.

Owed:
1. CONTRACTS-HTTP.md -- POST /v1/enroll gains a NEW 409 response. Body is the fixed string: "this client certificate is already bound to an agent; enrol with a fresh client keypair". It fires when the client certificate on the connection is already live-bound to a DIFFERENT agent. The connection is KEPT (invariant 10 -- a merely buggy client reaches it, and /v1/enroll is unauthenticated so the socket names no principal). The body deliberately does NOT name the agent holding the binding: that would make an unauthenticated route an oracle mapping a certificate to an agent id.
2. CONTRACTS-ONDISK.md -- the durable roster record now populates cert_bindings, e.g. "cert_bindings":[{"fp":"<64 lowercase hex>","bound_at":"<RFC3339>"}]. No new record type and NO migration: the field was reserved by ENROL-SHAPE and is bounded by MaxCertBindings=16; enrolment writes exactly one. Records written before MTLS-BIND have no cert_bindings key and remain valid -- empty is an ordinary value, not a damaged record.
3. DECISIONS.md -- two decisions a future reader WILL challenge, so record them with reasoning: (a) ABSENCE of a client certificate is ACCEPTED at enrolment (binds nothing, still 201), because the listener is tls.RequestClientCert which requests and never requires, so absence is the ordinary case; refusing would invent "a certificate is mandatory" in the wrong layer and lock out /healthz, the container healthcheck and every client without a keypair. The migration-safe target is PER-AGENT enforcement (MTLS-CROSSCHECK). (b) A presented certificate that is EXPIRED or NOT YET VALID is IGNORED (attaches nothing, request still served, discard logged at Info with the fingerprint), never made into a durable binding -- crypto/tls does not check dates, and this uses crypto/x509's verdict via the existing checkClientCertValidity, matching RELAY-20's peer-plane precedent.
4. AGENT_LOG.md -- a dated MTLS-BIND entry.

Note: docs must NOT claim a cross-check is enforced. MTLS-BIND creates the FACT only; enforcement is MTLS-CROSSCHECK.
