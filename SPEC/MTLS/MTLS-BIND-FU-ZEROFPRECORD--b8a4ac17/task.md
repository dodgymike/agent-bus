## Description

internal/auth/record.go validateRosterEntry (~line 326) validates each CertBinding's BoundAt and RetiredAt but NEVER its Fingerprint, so a durable record carrying an all-zero fingerprint decodes cleanly and is stored as a LIVE binding.
The EXPLOITABLE path is already closed by MTLS-BIND: certFingerprintOwner now refuses the zero fingerprint up front (the zero value is what a caller holds when NO certificate was presented, and the idiomatic slip fp, _ := ClientCertFingerprintFromContext(ctx) produces it silently). internal/relay/peerstore.go guards the identical case on the peer plane.
Remaining work is defence in depth at the RECORD layer: decide whether Encode should refuse to write a zero fingerprint (server-side bug, 500) and whether Decode should discard such a record loudly at recovery (invariant 6). Deliberately left out of MTLS-BIND as scope creep, since it changes recovery behaviour.
