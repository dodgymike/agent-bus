## Description

SECURITY FOLLOW-UP discovered during cea09b96. A package-controlled TestMain can bypass m.Run(), print forged verbose RUN/PASS markers, and exit 0; proof-check then reports PASS although no genuine test ran. Conversely, TestMain can run a failing test, print a forged empty-package summary, and force exit 0; parser precedence can downgrade genuine failure to VACUOUS. Both plain and go -json streams ultimately include unauthenticated test-process stdout, so marker parsing alone cannot establish execution authenticity. This is distinct from cea09b96 original accidental-vacuity defect (indented subtest accounting and parent-PASS/all-children-SKIP), and must not expand that focused fix inline. DESIGN FIRST: define proof-check trust/threat model. Either obtain harness-controlled evidence outside arbitrary test stdout (including selected-test enumeration, actual execution, and failure) and add adversarial regressions, or explicitly document that malicious repository test code/TestMain is outside the tool security boundary and ensure no claims imply otherwise. Acceptance: preserve failure-before-verdict; a TestMain omitting m.Run and forging PASS cannot yield PASS; a real failure followed by forged empty evidence cannot yield PASS or VACUOUS; cover plain and JSON modes; keep cea09b96 protections.
