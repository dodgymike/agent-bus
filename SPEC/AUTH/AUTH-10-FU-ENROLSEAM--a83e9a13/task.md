## Description

Security gate finding P2-1 on AUTH-10.

`agent-bus operator add` refuses a certificate fingerprint already live-bound to an enrolled AGENT
(cmd/agent-bus/operator.go). `auth.Service.Enrol` has NO equivalent check in the other direction, so
nothing structurally prevents an agent record and an operator record from naming one certificate.

WHY THIS IS P2 AND NOT P1: it is not remotely reachable. `EnrolRequest.ClientCertFingerprint` is a
TRANSPORT fact — internal/httpapi populates it from the actual TLS connection
(internal/httpapi/auth.go:345-359, clientcert.go:208-215) and the body decoder uses
DisallowUnknownFields — so an agent cannot claim a fingerprint it does not hold the private key for.
The residual is OPERATOR ERROR, not attack: security TESTED that
`agent-bus operator keygen -identity-dir <an existing AGENT identity dir>` silently reuses the
agent's certificate, because it calls client.LoadOrCreateClientCertificate on the same client-tls/
layout. AUTH-10 added a WARNING for that case; it did not add the structural refusal.

Do NOT wire this by handing auth.Service a nilable operator registry that fails open when unwired —
that reintroduces the "operators exist on disk but this process cannot see them" hazard AUTH-10
deliberately avoided. Make it structural or leave it to the CLI.

Note `peer add` performs no cross-plane certificate check at all; consider whether one rule should
cover all three principal kinds.
