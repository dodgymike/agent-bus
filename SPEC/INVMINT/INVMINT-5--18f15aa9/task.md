## Description

Once the running bus can mint, it should also be able to REVOKE and LIST invites without a stop. BLOCKED ON
INVMINT-3 (and transitively on INVMINT-1/-2).

This is the task most likely to be descoped, and that is fine -- it is filed so the decision is explicit
rather than forgotten. Complete it, or close it with a reason.

## Why it belongs in this epic

Invariant 3 requires invites to be single-use, EXPIRING AND REVOCABLE. Revocation that needs a bus stop is
the same operational gap as minting that needs a bus stop, with a worse profile: you revoke an invite
precisely when you believe it has LEAKED, and "schedule a maintenance window first" is the wrong answer to
a leaked credential. Arguably revocation is the stronger case for this epic than minting is -- minting has
the pre-minted-pool workaround (see the epic description), and revocation has no equivalent.

## Requirements

- Same operator principal, same authentication, same fail-closed posture as INVMINT-3.
- LISTING MUST NOT DISCLOSE SECRETS. List invite IDs, labels, TTL/expiry and spent/revoked state -- never
  the secret, not even truncated. The label is "an operator note... never echoed to a client"
  (`internal/invite/store.go:274-276`); listing to the OPERATOR is a different audience, but say so
  explicitly rather than letting it happen by default.
- Revocation is durable (invariants 4/5) and idempotent: revoking an already-revoked invite is a legitimate
  retry, returns the original result, and does NOT disconnect (invariant 10).
- Do NOT introduce a which-sentinel oracle. Enrolment already collapses its refusals to a single
  `invite not accepted` with no oracle distinguishing spent from revoked from unknown from expired --
  verified behaviour, and a listing/revocation surface must not hand an attacker the distinction the
  enrolment path deliberately withholds. Check whether an existing test pins that collapse before you
  change anything near it.
- Invariant 7: subcommand + `AGENT_PROTOCOL.md` entry in this task. `CONTRACTS-HTTP.md` and
  `CONTRACTS-CLI.md` updated.
- Note the offline contrast: `agent-bus peer list` writes nothing yet STILL takes the dirlock, because a
  read racing an append can see a half-written tail record (`CONTRACTS-CLI.md:311-316`). An ONLINE listing
  is served by the process that owns the log, so it does not have that problem -- but say so, do not assume
  it.
