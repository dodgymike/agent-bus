## Description

A security re-gate must audit only what changed since its own prior verdict, citing that verdict's commit sha or note number, rather than re-reading the whole change. This is where the observed 1.7x re-gate multiplier lives (60 security verdict notes over 35 tasks; 18 of 35 tasks needed 2+ security passes, two needed 3, one needed 4, one needed 5). Most re-gates currently re-audit the entire change rather than the delta since the last verdict.

ACK-5's final security pass was explicitly a delta review and is the right shape -- but it happened once, at the end, by accident rather than policy.

Definition of done: the security agent definition in .claude/agents/security.md instructs delta-scoping on any re-gate, names what must be cited (prior verdict + sha), and states the exception -- a re-gate goes full-scope when the change touched an invariant plane the prior pass cleared, because the prior clearance no longer holds.

Do not collapse security review into a single commit-time pass like integrator. The integrator's checks are mechanical and context-free (does HEAD compile, are deletions zero, is the pathspec scoped); security review needs intent and threat model, which is cheap while the implementer is live and expensive to reconstruct at commit time. Evidence: ACK-5's security gate promoted the unmetered outbound peer request to blocking, closed by a per-upstream cap -- an architectural fix that would have meant shipping a hole or unwinding dependent work if found at commit time.
