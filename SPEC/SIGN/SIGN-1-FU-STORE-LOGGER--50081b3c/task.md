## Description

Filed 2026-08-14 by the SIGN-1-FU-OUTOFORDER-POISON security gate (finding LOW).

internal/hub/hub.go builds store.New(store.Options{MaxAge, MaxBytes, Now}) and passes NO Logger. SIGN-1-FU-OUTOFORDER-POISON added store.Options.Logger and defaulted it to logging.New(os.Stderr, logging.LevelWarn) -- deliberately NOT the repo's usual io.Discard default, because a discarding default would make the real bus SILENT on the one event invariant 6 names, and internal/hub was outside that task's file boundary so it could not be wired up there.

CONSEQUENCE TODAY: store's two WARN lines (the ordinary late insert, and the at-or-below-prunedHead non-retention) go to RAW os.Stderr at a FIXED WARN threshold. They bypass the operator's configured logger, ignore the configured level, and are unassertable from the hub's log buffer -- confirmed by the gate: `hub log contains 'retention'? false`.

THE FIX: pass h.log into store.Options.Logger at the store.New call site in internal/hub/hub.go. KEEP the os.Stderr default in internal/store -- it is the fail-loud default for any other caller, and once the hub passes its own logger the default stops mattering. Add a hub test asserting the store's discard line lands in the hub's log buffer.

---
APPENDED 2026-08-14 -- SECOND HALF OF THIS FIX, from the SIGN-1-FU-OUTOFORDER-POISON security re-verification. The two store WARN lines are UNCAPPED ON THE RECOVERY PATH and that is a measured defect, not a theoretical one.

MEASURED: replay calls store.Append for every record in the log and the log is NEVER compacted, so the re-emission bound is the number of out-of-order records EVER WRITTEN, not the retained set. With MaxBytes=20, replaying 20 out-of-order pairs emitted 20 WARN lines with a retained set of 2. At the hub level, 63 late inserts re-emit 63 lines / 26,316 bytes on restart 1, 2 AND 3 with a DURABLE DELTA OF ZERO; 5 rounds of 64 accumulate linearly to 315 lines / 132,338 bytes on every start. Once records age past MaxAge the OTHER branch fires instead, at 564 B/line -- 1.34x worse.

WHY IT MATTERS: internal/hub/hub.go:55 maxDecodeFailuresLogged=8 caps the analogous replay line one layer up for exactly this reason, and these uncapped store lines interleave with -- and can drown -- the capped invariant-6 recovery DISCARD errors. Compounding it, hub.go:527 builds store.New WITHOUT Options.Logger, so a hub opened at LevelDebug saw 63 lines on raw stderr and ZERO in its configured logger buffer: -log-level cannot suppress them, nothing redirects them, they carry none of the hub's base fields, every hub test asserting on the log buffer is blind to them, and docker-compose.yml has NO logging: block (verified) so the container inherits Docker's unbounded json-file driver.

SCOPE, therefore, is BOTH halves at the one call site: (a) pass o.Logger into store.New at internal/hub/hub.go:527; (b) add the maxDecodeFailuresLogged one-shot-cap-plus-total pattern to BOTH store branches (internal/store/store.go, the m.Seq < s.head late-insert WARN and the m.Seq <= s.prunedHead non-retention WARN) -- or suppress per-record during replay and emit one summary at the end, which invariant 6 permits since the hub already does exactly that. store.go's comment on the late-insert branch already states the true (unbounded) bound and points here; correct it to match whichever shape is chosen.
