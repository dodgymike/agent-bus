## Description

NOT A LIVE VULNERABILITY TODAY. This is a tripwire to add BEFORE a future change lands, not a hole
to patch now.

auth.WALRoster.Apply does not filter foreign bus prefixes on replay, and internal/auth/floors.go
already anticipates that "a future peer-roster record legitimately carries one". Currently this is
NOT reachable by any remote client: the only writer of auth.RecordKind records is Service.Enrol,
and peer rosters live in the relay registry -- so getting a foreign-prefixed roster entry into the
WAL requires operator-level access to the data directory, not anything a network client can
trigger.

The day a peer-roster record is folded into authRoster, a foreign-prefixed id could complete a
session and become sender on /v1/ack/, and ACK-17's conclusion that the unqualified-name keying
mutation (mutation 2 / 2B in ACK-17) is UNOBSERVABLE would lapse -- two same-named agents on
different buses could then share a parked-wait bucket for real, which is the invariant-2 shape
(every agent id is fully qualified; never shorten it) ACK-17 flagged as a judgement call on
fixture cost rather than something exploitable today.

ACTION REQUIRED: whoever implements folding a peer-roster record into authRoster must, in the
SAME change, add a cross-bus keying test (a genuine two-bus fixture) proving the parked-wait
bucket -- and any other principal-keyed state -- is not shared across bus prefixes.

Source: security gate finding on ACK-17 (2026-08-21). Filed by spec-keeper at the direction of
feature-runner on ACK-17.
