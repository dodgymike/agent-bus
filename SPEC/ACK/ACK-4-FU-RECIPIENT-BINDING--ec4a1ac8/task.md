## Description

Found by the security gate during ACK-3 (2026-08-16). relay.AuthorizePeerAck (internal/relay/ack.go:669) authorises DeriveJobID(peer, correlationKey) ONLY. The second half of authorization merely asks whether an ACK row exists for (key, recipient) -- it does not check that THIS peer is the one this bus routed THAT RECIPIENT'S copy through. So a peer legitimately bound for key K may settle the row of ANY recipient of K, and terminal is ABSORBING, so the wrong outcome can never be corrected.
NOT REACHABLE IN THIS BUILD, which is why ACK-3 was not blocked on it: internal/hub/hub.go recordAcceptance returns early for relayed and broadcast messages, and a local send carries exactly one recipient, so no key ever has more than one row today. It becomes a real cross-peer forgery -- including burning the terminal for a LOCAL recipient -- the day multi-recipient local sends or relayed/broadcast rows land (ACK-CONTRACT.md 3.2's 'N rows'), and the outbox already fans one key to up to 8 peers.
Fix: make the second half of the binding recipient-aware, AND amend ACK-CONTRACT.md 6.2, whose rule as written is exactly what permits this. Must land before any task creates a second row for one correlation key.
