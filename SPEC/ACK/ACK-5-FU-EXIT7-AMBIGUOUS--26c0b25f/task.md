## Description

Found by the ACK-5 documentation gate, 2026-08-21, and verified against the code.

internal/httpapi/ack.go answers 501 in TWO places on the acknowledgement surface: the pre-existing ErrNoAckTable arm (this build has no delivery lifecycle table) and ACK-5 new transit arm (this build has no back-propagation seam wired). client/transport.go maps 501 to KindRejected, which client/errors.go maps to EXIT 7 -- the same exit code the agent-busctl ack help table documents solely as already terminal with a DIFFERENT outcome (a 409). So exit 7 now means either permanently unavailable on this build, do not retry or your outcome conflicts with a terminal that already stands, and the two are separable only by the human-readable message text.

That matters because the CLI's exit codes are a documented, machine-consumable contract for agents shelling out (invariant 7: stable documented exit codes), and an agent branching on the number alone cannot tell a permanent build limitation from a semantic conflict.

ACK-5 WIDENED this rather than introducing it -- 501 already mapped to exit 7 before the transit arm existed -- and it was deliberately not fixed inside ACK-5 because the fix belongs in the exit-code table, which is machine-parsed by cmd/agent-busctl/cli_test.go's TestHelpExitCodeTablesAgreeWithClientExitCodes, and changing it is a CLI-contract decision of its own.

Two candidate shapes: (a) give 501 its own exit code and update the parsed table plus that test; or (b) rule that exit 7 means rejected, do not retry generically and correct the help table to say so. (a) is more useful to an agent; (b) is smaller. Either way AGENT_PROTOCOL.md and both help tables must agree. ACK-5 documented the ambiguity in the ack help notice as an interim measure rather than leaving it undiscoverable.
