## Description

Found by the security gate on ACK-12-FU-WATCH-CORRELATION-KEY, 2026-08-21. `signing.Canonicalize` covers a message id and a sequence; for a RELAYED message the signature was made on the ORIGIN bus before any hop existed, so the preimage carries the ORIGINs pair -- `internal/relay/signed.go`, `RelayedMessage.CanonicalBytes` passes `MessageID: m.OriginMessageID, Sequence: m.OriginSeq`. But `client/canonical.go`s `signingMessage` feeds `m.MessageID`/`m.Seq`, which on a relayed message are the DESTINATION buss local mint. A recipient-side verifier built on it therefore reconstructs the wrong preimage and rejects every relayed message as signature-invalid. **Nothing verifies signatures on the client read path today, so nothing is broken right now** -- this is a trap for whoever switches verification on, and it is invariant 9s silent-failure class (compiles, tests pass, protects nothing). The fix is to feed `CorrelationKey` (landed by the parent task) and the sequence half parsed out of it, for the relayed case only. `CONTRACTS-HTTP.md` and `CONTRACTS-CLI.md` now document this gap by this exact key -- **closing it must also remove those two notes.** MUST be closed before any recipient-side signature verification ships.
