## Description

Raised as a LOW by the ACK-5 security gate, 2026-08-21.

relay.AuthorizePeerAckVia widens ACK-CONTRACT.md section 6.2's obligation binding with an INDIRECT arm whose final clause is PeerBaseURL(D) == PeerBaseURL(P) -- the address this bus would dial for destination D is the address it would dial for the acknowledging peer P, i.e. this bus's OWN routing table says P is the next hop for D.

That clause is sound TODAY only because Registry base URLs are operator-written: SetPeerBaseURL is the only writer, and Registry.UpsertPeer -- the HANDSHAKE path -- sets baseURL to the empty string for a new peer and preserves the existing value otherwise, so a peer cannot assert its own address. The security gate verified this by reading internal/relay/registry.go.

The risk is that nothing ENFORCES it. A future change that let a handshake, a roster update or any other peer-supplied input write baseURL would silently widen the binding arm -- a peer could make itself the apparent next hop for a destination and settle acknowledgements it has no standing to settle -- and NO TEST WOULD GO RED. This is the same class as the guards this project has repeatedly found could not fire.

Fix: an explicit guard test (an AST guard, or a behavioural test asserting UpsertPeer never writes a non-empty baseURL for a peer that had none) pinning that the only writer of Registry base URLs is operator configuration.

Noted as a possible stronger alternative: the -route-for durable record already carries the NEXT HOP'S TLS FINGERPRINT, which is a stronger and less spoofable signal than address-string equality, but Registry does not currently expose it. Binding on the fingerprint instead would remove the reliance on string equality altogether.
