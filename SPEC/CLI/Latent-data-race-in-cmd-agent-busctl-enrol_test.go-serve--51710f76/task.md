## Description

cmd/agent-busctl/enrol_test.go sets cmd.Stderr = &serverStderr (a bytes.Buffer) for the spawned agent-bus server and, in waitForHealthz, calls serverStderr.String() at line ~178 while that process is STILL RUNNING. os/exec copies the child's stderr into the buffer from its own goroutine and only synchronises on cmd.Wait(), so the read races the write. Confirmed by -race:

WARNING: DATA RACE
  bytes/buffer.go:207 ... io.go:413 ... os/exec/exec.go:407,544
  cmd/agent-busctl/enrol_test.go:178
  cmd/agent-busctl/enrol_test.go:88
--- FAIL: TestCLIEnrolEndToEnd (20.57s)
    testing.go:1319: race detected during execution of test

Why it has been invisible, and why that makes it worth fixing rather than tolerating: the racing line is only reached when the server FAILS to answer /healthz before the deadline. On a healthy tree the server starts, that branch never executes, and the suite is green -- so the race is latent. It fires precisely when something else is already broken, and then it REPLACES the diagnostic ("server stderr: ...") that the test exists to print with a race report. The one moment the message would be most useful is the one moment it is destroyed.

Discovered during MTLS-EXPIRY (3604af80-35a0-4007-818e-ef309fdeaf0c) while isolating whether a cmd/agent-busctl failure was caused by that task. It was not: enrol_test.go is UNMODIFIED at HEAD, and HEAD alone plus HEAD + the MTLS-EXPIRY client files both pass cleanly. It was exposed by the MTLS-LISTENER working-tree change making the bus TLS-only while this test still probes http:// + /healthz, which drives the timeout branch.

CLAUDE.md: "Tests run with -race. Concurrency here is the product; a data race is a P0." Rated P1 here only because it is confined to test scaffolding rather than the server, but it should not survive long.

Likely fix: guard the buffer with a mutex (a small syncBuffer wrapper implementing io.Writer), or capture stderr via an io.Pipe/cmd.StderrPipe and drain it in a goroutine, so the deadline path can read a snapshot safely. Do NOT "fix" it by removing the stderr from the message -- that message is the diagnostic.

Proof: go test -race -run TestCLIEnrolEndToEnd ./cmd/agent-busctl/... (must show no DATA RACE warning even when the server-start deadline path is forced, e.g. by pointing at a TLS-only listener)
