## Description

DECISION TASK -- the sharpest invariant question in this epic. This BLOCKS CONV-RECORD.

Invariant 6: **the append-only log records METADATA AND ROUTING ONLY -- never message bodies.** The
operator asked for "user-supplied metadata that 'names' or tags the conversation". A user-supplied
name/tag is ARBITRARY USER CONTENT. If the conversation record lives in the append-only log, that
content is now durably on disk in the one place invariant 6 says bodies must never go.

Ask it directly, and answer it: **is a conversation name metadata, or is it a body wearing
metadata's clothes?** A 64KB "name" is plainly a body. A 32-byte slug plainly is not. The boundary
is what this task must fix, and the answer must be a bound, not a vibe.

CONTRAST, so the two are not lumped together: the CREATOR is a fully-qualified agent id --
routing/identity metadata -- and sits comfortably inside invariant 6. The NAME does not get that
free pass.

MANDATORY OUTCOMES regardless of ruling:
  - The name MUST be LENGTH-BOUNDED and CHARACTER-BOUNDED. Compare `store.MaxBodyBytes = 64 << 10`
    (internal/store/message.go) -- a name bound anywhere near that is evidence the ruling is wrong.
  - The epic MUST state whether this is an AT-REST EXPOSURE: the log is not encrypted, so a name is
    readable by anyone who can read the data directory, forever, and is NOT covered by any
    retention window that applies to bodies.
  - Consider explicitly whether the name should be excluded from RELAY export to peers.

READ IN FULL BEFORE RULING: INVARIANTS.md invariant 6.

  2. Reasoning for the bound -- why THAT number -- not just the number.
