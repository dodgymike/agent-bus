## Description

The operator was explicit: **"The client starts the conversation by using the client binary to ask
the server to create the conversation, with receipients."** So the CLI is CENTRAL here, not
incidental.

Implement conversation creation: the client supplies the recipient list and the user-supplied
name/tags; the SERVER mints the id (invariant 1 -- the server is authoritative on every id, never a
client) and returns the full record.

INVARIANT 1 TRAP, and it has bitten this repo: a client-supplied conversation id must be treated as
INPUT TO VALIDATE, NEVER AS AN ASSIGNMENT TO TRUST. See the `SendRequestBody.Sender` doc at
internal/httpapi/messages.go for the exact shape of the guard and WHY it exists -- the sender field
"EXISTS ONLY SO SIGN-6 CHECK (d) CAN BE MADE. IT IS INPUT TO VALIDATE, NEVER AN IDENTITY." Any
conversation id echoed by a client gets the same treatment.

The route authenticates like every other route (invariant 3: every route authenticates except
enrolment, session begin/complete, /healthz and /v1/info). The authenticated principal from the
REQUEST CONTEXT is the creator -- never a body field.

INVARIANT 7 (same task, non-negotiable): ship the `cmd/agent-busctl` subcommand AND the
AGENT_PROTOCOL.md entry IN THIS TASK -- a capability without its CLI surface is the missing half of
the task, not a follow-up. `--json` everywhere, stable documented exit codes, no interactive prompt.
`scripts/bus-*.sh` wrappers are RETIRED; adding one is FORBIDDEN (only bus-serve.sh survives). The
client package cannot live under `internal/`. Verify by running the COMPILED CLI against a running
server -- never hand-written curl.

Definition of done:
  1. The HTTP route, with the server minting the id and recording the creator from the request
     context.
  2. `agent-busctl` subcommand that creates a conversation with multiple recipients and a name,
     `--json` output, documented exit codes.

  4. Proof exercised through the COMPILED CLI against a running server.
