## Description

DECISION TASK. Do NOT quietly pick one; produce a ruling with reasoning and record it in
DECISIONS.md.

The operator asked for a "server-supplied uuid", which is correctly server-authoritative (invariant
1: the server is authoritative on every id, ids are never reused including across restarts). That
part is settled.

WHAT IS NOT SETTLED: **a bare UUID is not NAMESPACED.** Every other id in this system is --
`bus-xxx-11`, `inv-xxx`, and agent ids are FULLY QUALIFIED `<bus-id>.<agent-id>` precisely so
cross-bus routing is unambiguous (invariant 2). The operator's own request implies a conversation
SPANS BUSES: "when a server first receives a conversation message it should start tracking it". So
two buses could in principle mint ids that are unattributable to a minting authority.

**A UUID's collision resistance is NOT the issue. ATTRIBUTION is.** Given a conversation id off the
wire, can a bus say which bus minted it, and is that answer verifiable? With `<bus-id>.<conv-id>` it
is structural; with a bare UUID it is not, and you have lost exactly the property invariant 2 exists
to provide.

READ IN FULL BEFORE RULING: INVARIANTS.md invariants 1 and 2.

Definition of done:
  1. docs/conv/ID-SHAPE-DECISION.md with a line `RULING: BARE_UUID` or `RULING: BUS_QUALIFIED`,
     the reasoning, and explicit treatment of the cross-bus attribution question and of what
     invariant 2 does or does not require here.
  2. If the ruling is BARE_UUID, it must state what REPLACES the attribution property and why that
     is acceptable -- "UUIDs don't collide" is NOT an answer to the attribution question.
  3. A DECISIONS.md entry.

Blocks CONV-RECORD -- the record format cannot be fixed before the id shape is.
