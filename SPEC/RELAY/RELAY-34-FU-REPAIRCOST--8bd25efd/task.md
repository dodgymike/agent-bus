## Description

reconcileWithdrawalFloor (internal/relay/peerstore.go) repairs the durable withdrawal floor from each withdrawal the log still holds, and recordWithdrawal rewrites the WHOLE file on every raise. So repairing a lost floor over a log holding N withdrawals costs N full rewrites and ~2N fsyncs.

MEASURED by the RELAY-34 security gate at 300 withdrawals: ~27ms on a healthy start (the floor already covers everything, so recordWithdrawal returns without I/O) versus ~1.16s when the floor has been lost and every withdrawal must be re-floored.

Judged out of scope for RELAY-34 and accepted by the security gate: it is a ONE-TIME cost on an abnormal start, it happens under the dirlock, it is logged loudly per repair, and it is bounded by maxPeerWithdrawalFloorEntries (4096). But it is O(N^2) bytes written in N, and a coalesced repair -- collect the raises during replay and write once at the end -- would make it one rewrite. Needs an end-of-replay hook, which PeerStore does not currently have; that is why it was not done inline.
