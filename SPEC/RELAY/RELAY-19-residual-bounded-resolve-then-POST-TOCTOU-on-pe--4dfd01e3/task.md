## Description

internal/relay/forward.go's attempt()/resumeJob resolve a peer's base URL via
Registry.PeerBaseURL BEFORE issuing the outbound POST (forward.go around :1271-1300, and the Resume
path documented at :1407). If the peer is revoked/de-peered in the WINDOW between that resolve and
the POST actually landing, the request can still be sent to an address that was valid at resolve
time but is no longer trusted by the time it arrives -- a bounded resolve->POST TOCTOU. Reported
PASS (no P0/P1) by RELAY-19's security gate, 2026-08-14, as finding (2) under Revocation holds,
noted as inherent and bounded by the per-attempt Timeout (30s default).

Not currently exploitable beyond the existing bound: de-peering takes effect on the NEXT attempt and
on Resume, both of which re-resolve before offering, so the exposure is at most one in-flight
request per revoked peer, capped by Timeout. This task is to either (a) shrink the window further --
e.g. a final PeerBaseURL liveness check immediately before the POST is issued rather than only at
the top of attempt(), or (b) explicitly accept the bound and document WHY it is acceptable
(DECISIONS.md) rather than leaving it as an implicit residual, so a future reviewer does not have to
rediscover the same reasoning from scratch.

Source: RELAY-19 file-followups brief item 4 (security P2s), 2026-08-14.
