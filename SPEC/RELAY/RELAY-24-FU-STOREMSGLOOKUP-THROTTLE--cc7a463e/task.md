## Description

LOW-severity hardening item, found during the security audit of RELAY-24-FU-STOREMSGLOOKUP (c6530638-7cca-4404-bc61-88ca6c2d30b9), rated non-blocking (L2 in that review, referenced again in the second security response).

Store.Append's duplicate-OriginMessageID branch logs its ERROR line ONCE PER PROCESS (a log-once + counter throttle mirroring hub.idemCapWarned), to avoid a peer-driven log flood -- see security's M1 finding on RELAY-24-FU-STOREMSGLOOKUP: this branch is peer-triggerable (the relay idempotency scope is (sender, OpRelay, origin id), the sender label is peer-asserted, and hub.relayedOrigin binds only the bus halves, never the agent half), so a peer presenting the same origin id under two attested sender labels within its own namespace can drive tens of thousands of these before idem's pressure line.

PROBLEM: the throttle is UNCONDITIONAL (one line total, ever, per process), so a peer can deliberately or incidentally burn the single log line EARLY on their own harmless/adversarial traffic, and that MASKS a LATER, genuinely interesting duplicate -- e.g. one caused by a write-path or recovery bug rather than by a peer replaying a sender label. DuplicateOriginMessageIDs() (the counter) still increments on every occurrence and the operator doc says to correlate the counter against the single log line, but once the line has fired, a later spike in the counter has no accompanying detail (origin id, both local ids, sender) to investigate with.

Relevant to invariant 6: every discard/anomaly must be logged loudly and specifically -- an unconditionally-exhausted throttle degrades "specifically" back toward "loudly but generic" for every occurrence after the first.

SUGGESTED FIX: re-arm the throttle per origin bus (e.g. a small set/map of already-warned origin bus ids, or a per-origin-bus log-once flag) rather than a single process-wide bool, so one peer exhausting its own warning does not silence the diagnostic for a different peer's later duplicate. Bound the set size sensibly (it is inherently bounded by the number of distinct peer origin buses, which is small relative to message volume). Alternative: time-based re-arm (e.g. log at most once per N minutes) if a peer-bus-keyed set is judged not worth the complexity.

Not urgent: the counter still moves and is documented as the thing to correlate, so nothing is silently lost -- this only degrades the diagnostic detail available after the first occurrence.
