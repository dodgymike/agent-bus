## Description

Found while testing RELAY-52-FU-HUBDISCARDS (internal/hub/discard_relay52fu_test.go). internal/hub/hub.go emits TWO applied-key discard lines with no cap and no one-shot notice: the 'could not be remembered' line in Apply (~hub.go:1187, idem.Recover fails) and the 'could not be decoded' line in recoverIdemRecord (~hub.go:1207, idem.DecodeRecord fails). Both are ERROR-level, one line per entry, with nothing bounding the count.

Contrast the function immediately above (Apply's undecodable-message-record branch): it caps itself at maxDecodeFailuresLogged, logs a one-shot 'further ... will NOT be logged individually' notice when the cap is reached, and the exact total is still reported via the end-of-recovery summary. That is the local precedent to copy, not invent -- same shape, different counter.

Trigger: an idem-record schema bump (idem.DecodeRecord uses DisallowUnknownFields, so a build downgrade or a record written by a newer build hits this on every entry) or a charset/length-validator change (idem.ValidateKey vs store's length-only bound) hits this on every pre-existing applied-key record. Either produces one ERROR per message on exactly the restart an operator most needs to be able to read, unbounded.

OBSERVED RED (2026-08-21, spec-keeper): overlay probe TestProbeAppliedKeyRememberDiscardsShouldBeCapped, built on the existing hubfuRecover/hubfuMessageRecord/hubfuUnacceptableKey fixtures, injected decodeCap+3 (11, measured against this build's maxDecodeFailuresLogged=8) pre-IDEM-11 records whose idempotency key idem.ValidateKey refuses. All 11 were logged individually with no cap:
  probe2_test.go:41: RED (expected today): 11 individual "DISCARDING an applied-key record that could not be remembered during recovery..." lines were emitted for one flood event with no cap and no one-shot notice.

Fix shape (not prescribed): add a counter + one-shot cap notice + end-of-recovery total for each of the two applied-key discard lines, mirroring the undecodable-message-record shape. Note this WILL require updating internal/hub/discard_relay52fu_test.go's own assertions, which currently pin these two lines as firing once per entry with no cap (that pinning is deliberate per that task's own notes, not an oversight) -- land the production fix and the test update together.
