## Description

P2, but a HARD PREREQUISITE for enabling broadcast relay -- title/description say so explicitly because this must not be missed when /v1/broadcast or relayed broadcast support is turned on.

relay.Registry.BroadcastTargets returns EVERY configured peer regardless of the message's actual recipients, and Forwarder.Enqueue performs 2 fsyncs per target (one wal.Log.Write call = a PREPARE and a COMMIT, each with an unconditional fsync). At MaxPeers = 64 that is 128 serial fsyncs holding the hub's global writeMu, and it is repeatable by any enrolled local agent simply by broadcasting.

This is LATENT today, not yet exploitable: /v1/broadcast currently returns 501, and a relayed broadcast that did reach a peer is refused there with ErrUnsignable (internal/relay/message.go:698-700). But the egress envelope already carries `Broadcast: m.Broadcast`, so the trap is wired and waiting for the day broadcast is turned on -- discovered during RELAY-24-BLOCKER-EGRESS (85ae8b32-3a46-4e85-bdfe-ea29730670fb) while reviewing the egress wiring.

Fix shape: BroadcastTargets should filter to peers that actually host a recipient (or an explicit fan-out policy), and/or the per-target fsyncs should be batched into a single group commit rather than one serial fsync pair per peer while holding writeMu. Do not enable broadcast relay without addressing this.

Note the adjacent-but-NOT-identical existing task RELAY-2-FU-BROADCAST-FANOUT (8b5319e1-5683-4aa5-ad98-746074e206a8): that task is about wasted round-trips against peers that will always answer 400 (no correctness/perf risk, P3). THIS task is about writeMu-held fsync amplification (a real perf/availability risk once fan-out succeeds). Wired relates, not duplicated.

Invariants to read before implementing: 4 (never trade durability for latency, but batching a group commit does not weaken it), 5 (memory serving copy / disk truth), 11 (relay/federation transport).
