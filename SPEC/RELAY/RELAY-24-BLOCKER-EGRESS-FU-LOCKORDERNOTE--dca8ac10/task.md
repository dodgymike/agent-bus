## Description

internal/hub/hub.go:381-385 states the total order as writeMu -> {waitMu, store lock, roster lock} and rules that "an Egress implementation may take a lock that is a LEAF with respect to the hub". But the shipped relayEgress takes ob.mu and log.mu through Forwarder.Enqueue, and ob.mu is NOT a leaf (log.mu -> ob.mu via Apply). The order is still acyclic, so there is no live deadlock -- but the enumerated set omits both locks and the stated rule is narrower than what ships, in a note whose entire purpose is that a false lock-order comment is how the next deadlock gets written. Minimal fix: list log.mu and ob.mu, and restate the rule as "must not take a lock from which the hub's own lock is reachable".
