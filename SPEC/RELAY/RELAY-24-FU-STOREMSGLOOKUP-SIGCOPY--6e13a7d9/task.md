## Description

Pre-existing defect at HEAD, found during RELAY-24-FU-STOREMSGLOOKUP review and security audit (2026-08-14/15), reported OUT OF THAT TASK'S BOUNDARY.

store.copyMessage deep-copies Body, Recipients and BusPath, all []byte or []byte-bearing types -- but Signature, which is also a []byte, is aliased rather than copied. This was already live on the Since read path (the ordinary message-fetch path every client hits); RELAY-24-FU-STOREMSGLOOKUP added two more exit points through the same function, ByID and ByOriginMessageID, which widen the blast radius without being its cause.

Impact: a caller mutating a returned Message's Signature field corrupts the SERVING COPY held by the store -- the in-memory record every subsequent reader sees. This bears directly on invariant 5 (memory is the serving copy; disk is the truth) and on signature verification: a mutated signature can desync the served copy from what was actually signed and durably written, corrupting verification for every later reader of that message, not just the caller who mutated it.

Fix: copyMessage must clone Signature the same way it clones Body/Recipients/BusPath (append([]byte(nil), m.Signature...) or equivalent). Also correct copyMessage's doc comment, which says "the two slices" while the function actually copies three (Body, Recipients, BusPath) plus now needs to copy a fourth (Signature).

Add a test pinning the Since exit point specifically (the live read path), not only the two new lookups, since that is the pre-existing and highest-traffic exposure.

Reported by: reviewer (finding 8 in code review) and security (independently, in the audit) on RELAY-24-FU-STOREMSGLOOKUP (c6530638-7cca-4404-bc61-88ca6c2d30b9), both agreeing it warrants its own task rather than being folded into that one.
