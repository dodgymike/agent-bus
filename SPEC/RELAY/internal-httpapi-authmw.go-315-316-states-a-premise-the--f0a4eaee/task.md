## Description

Filed 2026-08-14, from RELAY-6's gate findings.

CONTRADICTION, VERIFIED LIVE IN CODE (not a doc, not stale prose -- two comments in the SAME package directly disagree): internal/httpapi/authmw.go:315-316 states verbatim: "A peer bus is not an enrolled agent. It holds no session token and there is no route through which it could obtain one, so a bearer requirement here would be UNSATISFIABLE rather than strict." internal/httpapi/peerprincipal.go:195-197 says the opposite: "A peer bus is also an enrolled principal on the buses it peers with, so a peer request may well carry a valid session token, and authMiddleware may already have attached the resulting agent principal." The security gate that surfaced this confirms peerprincipal.go is right: a peer bus enrolls as an ordinary agent principal wherever it peers, so it CAN obtain and present a session token.

THE BEHAVIOUR IS CORRECT; THE JUSTIFICATION IS NOT, AND THAT IS THE DANGEROUS PART. authmw.go's peer-route allow-list is fine as SHIPPED -- peer routes stay gated by RequirePeerPrincipal regardless of this comment. But the comment reasons from a false premise ("unsatisfiable") to a conclusion ("therefore an allow-list is safe here, the same shape as /v1/session/complete") that a future maintainer reading ONLY this comment would extend by putting a peer path directly on unauthenticatedRoutes -- the exact thing two separate guards exist to prevent (RequirePeerPrincipal's fail-closed resolver chain, and the derived-not-declared peerRoutes set the same comment block correctly describes lower down). A wrong reason for a right behaviour is more dangerous than a wrong behaviour, because it survives review: nothing about the shipped code is broken today, so no test catches the false premise, and the next person to touch this file inherits a justification that argues for the wrong extension.

SCOPE: correct authmw.go:315-316 (and the surrounding paragraph as needed) to state the true reason peer routes belong on this allow-list -- NOT because a peer bus cannot obtain a session token (it can, via ordinary agent enrolment on a peering bus), but because [whoever picks this up should re-derive the actual correct justification from peerprincipal.go's own reasoning: the AGENT principal a peer might carry is deliberately REMOVED/ignored by RequirePeerPrincipal's wrapper rather than trusted, specifically so a session credential is never accepted as a peer-bus credential -- see peerprincipal.go's own "THE AGENT PRINCIPAL IS REMOVED, NOT MERELY IGNORED" section for the correct framing to cite instead]. Do not merely delete the false claim; replace it with the true one, since the paragraph's conclusion (this allow-list is safe) still needs a correct supporting reason, not just a removed wrong one.
