## Description

Found while testing RELAY-52-FU-HUBDISCARDS (internal/hub/discard_relay52fu_test.go). internal/hub/hub.go's Apply, on a message record that DECODES but store.Append refuses (the DISCARDING a message record that could not be applied during recovery line, ~hub.go:1126), increments NO counter. Contrast the sibling branch a few lines above (undecodable-message-record discard) which increments h.undecodableMessages, and roster.go's noteRecoveredIdentities (~line 351) which checks ONLY h.undecodableMessages before emitting THE AGENT-ID REUSE CHECK RAN ON INCOMPLETE INPUT.

Measured via a throwaway overlay probe (git archive HEAD + one added test file, deleted after, never committed): a fixture that drives exactly one apply-branch discard (a message record present twice in the WAL, the only replay-reachable store.Append error) emits 1 DISCARDING a message record that could not be applied line and ZERO summary lines. The id-reuse detector then reports a CLEAN result -- summary absent, so roster.go's noteRecoveredIdentities never warns -- having silently missed the sender/recipient ids that discarded record named. Per invariant 6, a discard must be logged loudly AND specifically; a discard that no summary counts is exactly the silent-discard failure the invariant exists to forbid, expressed at the SUMMARY level rather than the per-line level (the per-line log call itself is loud and specific -- this is about the aggregate signal an operator actually watches).
