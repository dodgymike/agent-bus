## Description

LOW-severity hardening item / known-gap record, found during the security audit of RELAY-24-FU-STOREMSGLOOKUP (c6530638-7cca-4404-bc61-88ca6c2d30b9): "GATES/LIMITS recorded, none blocking" item (1) in the second security response.

internal/store/guard_relay24fu_test.go is an AST guard (go/parser + go/ast walk on ast.SelectorExpr) that bans call sites of Store.ByID and Store.ByOriginMessageID from internal/httpapi, client/ and cmd/agent-busctl -- because those two lookups do NOT apply Message.VisibleTo (the read path's authorization boundary: recipient filtering + the enrolment-epoch check), so a request handler calling them directly would bypass authorization over the trivially enumerable "<bus-id>-<n>" message-id namespace.

GAP: the guard matches by SELECTOR NAME (Sel.Name == "ByID" or "ByOriginMessageID"), deliberately broad and type-free (proving the receiver type would need go/types and would miss what it could not resolve). This means it catches direct calls, chained calls (h.Store().ByID(...)), method values, and interface-asserted calls -- but it does NOT catch INDIRECTION through a new, unguarded package. Specifically: if someone later adds a new EXPORTED wrapper function in internal/hub (e.g. hub.Hub.LookupMessageByID(id) that internally calls store.ByID) and calls THAT wrapper from an HTTP handler, the guard passes cleanly -- internal/hub is deliberately not in the guard's scanned set (lookupGuardDirs: internal/httpapi, client, cmd/agent-busctl), and the wrapper's own selector name is not ByID or ByOriginMessageID, so no scanned file references the banned names at all.

This is recorded as a KNOWN, INTENTIONAL-FOR-NOW gap (security's own characterization), not a defect to fix reactively -- the guard's escape-hatch subtest already tracks the ONE currently-open indirection point (hub.Hub.Store(), hub.go:902) and asserts it stays scanned-for AS LONG AS that accessor exists. The point of THIS task is to make sure a future reader does not mistake "the guard exists" for "the guard has complete coverage" -- the danger is exactly that a reviewer sees a green AST guard and assumes VisibleTo-bypass is closed, when it is only closed for the CURRENT set of indirection points.

SUGGESTED WORK (pick one, or both):
(a) Extend guard_relay24fu_test.go's doc comment / add an explicit code comment at the lookupGuardDirs declaration stating this limitation plainly, so it is visible at the guard site itself, not only in a task description.
(b) Consider widening the guard to also scan internal/hub for NEW exported wrapper functions whose body calls ByID/ByOriginMessageID and are not the already-tracked Store() accessor -- i.e. detect a NEW indirection point being introduced, not just direct calls from the three currently-guarded trees. This is more work and may not be worth it if internal/hub wrappers around these two methods are expected to stay rare/reviewed.

Not urgent: zero non-test callers of either method exist anywhere in the repo today (verified by security), so this is a preventive record, not an active exposure.
