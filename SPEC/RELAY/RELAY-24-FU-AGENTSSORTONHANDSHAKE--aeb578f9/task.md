## Description

internal/hub's h.Agents() re-sorts the roster on every call, and it is called on every peer handshake (the federation path RELAY-24 / commit 7095231 just made reachable in production). Trivial cost today at small roster sizes, but it is now on a path a remote peer can trigger repeatedly (each handshake), so it is worth caching/avoiding the re-sort rather than paying O(n log n) per handshake for an unchanged roster.

Found during the reviewer's pass on RELAY-24 (e303c624-3062-446d-9efc-86a9284220d3, "Composition root: wire federation into cmd/agent-bus/main.go"); filed as a non-blocking P4 finding from that review.

PROOF: names a Go test/benchmark to ADD (it does not exist yet) -- TestAgentsRosterNotResortedWhenUnchanged in internal/hub, instrumenting or wrapping the sort comparator (or counting calls to sort.Slice/sort.Sort within Agents()) across two consecutive Agents() calls with no roster mutation between them, and asserting the sort does not run the second time. Not required to be observed RED first (this is an efficiency finding, not a correctness fix), but the test should fail against the current always-sort implementation and pass once a cached/dirty-flag approach lands.
