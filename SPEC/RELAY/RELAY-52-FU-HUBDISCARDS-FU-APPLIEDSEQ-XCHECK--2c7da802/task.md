The fixture type hubfuRecovered carries an appliedSeq field that each build closure DECLARES (the highest sequence it expects Hub.Apply to have successfully applied). hubfuAssertRunning uses that declared value as the floor for the invariant-1 mint-does-not-rewind assertion. Today the declared value is trusted and validated only INDIRECTLY, by the post-recovery mint call succeeding above it -- there is no direct cross-check against production's own bookkeeping of the same fact, which hub.go:793 already logs as applied_high_water (h.appliedSeq) at end of recovery.

Security's suggestion: have hubfuRecover read back applied_high_water from the recovered bus's own log (or an equivalent exposed value) and assert it against the fixture's declared appliedSeq, making a fixture that mis-declares its own floor in EITHER direction mechanically impossible, rather than relying on the mint-based check to catch it (which security separately verified does catch both directions today, by mutation -- see that task's notes). This is test-strengthening, not a production defect: no user-facing behaviour is wrong, and hub.go:793 already logs the true value.

Currently absent: grep -n 'applied_high_water' internal/hub/discard_relay52fu_test.go returns nothing.

Fix shape (not prescribed): parse applied_high_water out of the recovered bus's own log output (same logfmt parser the file already uses via relay52Records/relay52Field) inside hubfuRecover or hubfuAssertRunning, and assert it equals (or is >=) the build closure's declared appliedSeq.
