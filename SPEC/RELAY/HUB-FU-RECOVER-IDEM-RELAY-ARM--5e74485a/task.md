## Description

Filed 2026-08-14 from the RELAY-24-BLOCKER-HUBINGEST test-engineer report. LOW. TWO RELATED POINTS -- the reporting agent's stated mechanism was CORRECTED by feature-runner, and the corrected version is what follows.

(i) hub.recoverIdemRecord's pre-IDEM-11 BACK-COMPAT ARM rebuilds the idem scope as OpSend/OpBroadcast from the message record alone. There is NO OpRelay case, so a relayed record reaching that arm would recover under the WRONG operation. It is UNREACHABLE TODAY: relayed records always carry Entry.Idem, and pre-IDEM-11 logs contain no relayed traffic.

(ii) THE CORRECTION: a DECODE FAILURE of Entry.Idem does NOT fall through to that arm -- it returns (idem.Record{}, false) immediately. So the arm is not the route in. But the CONSEQUENCE of losing a relay applied key is still strictly worse than losing a local one: losing a LOCAL applied key means a duplicate message, while losing a RELAY key means the peer's next retry resolves as idem.OutcomeNew and is RE-FORWARDED onto the mesh.

THE DECISION THIS TASK OWES: whether the back-compat arm should REFUSE to rebuild for a message whose sender's bus half is not this bus (fail closed rather than rebuild under the wrong op). Record the decision either way -- "unreachable, deliberately left alone" is an acceptable outcome if it is written down.
