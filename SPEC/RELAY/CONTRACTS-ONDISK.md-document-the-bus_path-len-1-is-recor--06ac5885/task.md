## Description

Filed 2026-08-14, closing a gap flagged by spec-keeper on 2026-08-08 (RELAY-11's own notes) that never got its own tracked task -- CONTRACTS-ONDISK.md still has ZERO mentions of bus_path/BusPath as of this filing (verified by grep).

RELAY-11 (07824e55, done, commit d4a1985) shipped store.NewMessageWithBusPath, which refuses a path whose last hop is not the recording bus -- bus_path[len-1] is ALWAYS the bus whose record it is; a local send's path is always [busID]. This is SUBTLY DIFFERENT from the wire semantic already documented at PROTOCOL.md section 10 (~line 865-866): "the last element is always whichever bus most recently forwarded it." The two diverge because relay stamps its hop at EGRESS (internal/relay/message.go Forward -> AppendHop), so once relay ingest lands (RELAY-20/RELAY-21), a single message carries two distinct bus-path values in flight: the RECEIVED path (as forwarded by the previous hop, not yet including this bus) and the RECORDED path (this bus appended, per the RELAY-11 constructor contract).

SCOPE: add a CONTRACTS-ONDISK.md section stating both invariants side by side (the on-disk RECORDED-path invariant vs. the wire RECEIVED-path semantic already at PROTOCOL.md ~865-866) and naming the divergence explicitly, so a relay-ingest implementer (RELAY-20/21) does not assume the wire and on-disk semantics are the same field. See RELAY-11's own reviewer notes (kind=response, P2-6/P2-7/P2-8, 2026-08-08) for the exact citation drift this already produced in code comments -- start there rather than re-deriving.

Was NOT RELAY-11's own scope (its owned files were internal/store/message.go, internal/hub/hub.go, internal/hub/audit.go, internal/hub/buspath_test.go only -- CONTRACTS-ONDISK.md was never in that boundary), which is why RELAY-11 could complete without this landing. P2, not blocking anything on the live critical path today, but should land before or alongside RELAY-20/21 (relay ingest) so the divergence is documented before code that could get it wrong exists.
