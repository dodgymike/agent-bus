## Description

cmd/agent-bus/main.go:936 emits an INFO line reading "no peer records and no peer trust records" whenever both come back empty. But internal/relay/peerstore.go's ActivePeers() (:2978) and TrustedBuses() (:3006) are ACTIVE-ONLY -- a bus whose peer configuration has been fully WITHDRAWN (every PeerRecord and BusTrustRecord tombstoned/removed) also reports zero from both, so the SAME message fires as for a bus that was never configured at all. An operator who withdrew a peer and is now debugging a federation problem reads a message that says they never configured one -- wrong-by-omission, same class as the false remedy string fixed in commit 7095231 (invariant 6: recovery discards etc. must be logged loudly AND SPECIFICALLY; the same specificity bar applies to any startup diagnostic on this path). Fix: distinguish "never configured" from "configured then withdrawn" in the log message -- e.g. consult a withdrawn/tombstone count (or the store's raw entry count before the active-only filter) and choose distinct wording.

Found during the reviewer's pass on RELAY-24 (e303c624-3062-446d-9efc-86a9284220d3, "Composition root: wire federation into cmd/agent-bus/main.go"); filed as a non-blocking P3 finding from that review.

PROOF: names a Go test to ADD (it does not exist yet) -- TestStartupPeerSummaryDistinguishesWithdrawnFromNeverConfigured in cmd/agent-bus. It must seed a peer store with a PeerRecord + BusTrustRecord and then withdraw/remove both (so ActivePeers()==0 and TrustedBuses()==0, matching the never-configured case), capture the startup log output, and assert the withdrawn case's message differs from (is not byte-identical to) the never-configured case's message. MUST be observed RED before the fix (today the two cases produce the identical string, so the differentiation assertion fails / the test does not yet exist) and GREEN after.
