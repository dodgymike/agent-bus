## Description

FILED 2026-08-16 by main. RELAY-23 landed the wire-version FIELD as CODE ONLY. This task is the
rollout, and it exists because deploying RELAY-23 carelessly LOSES MESSAGES PERMANENTLY.

# The hazard, verified independently by main

  internal/relay/handshake.go:334   dec.DisallowUnknownFields()
  internal/relay/client.go:78-84    Retriable() is TRUE only for 408, 429 and 5xx

Chain: a pre-RELAY-23 peer receives a frame carrying the new protocol_version field -> its strict
decoder rejects the unknown field -> it answers 400 invalid_request -> the SENDER classifies 400 as
FINAL, not retriable -> the message is ABANDONED, not retried.

Loss is TOTAL for the affected link, not partial: both the first-hop path and the restart-resume
path emit through Forward, so no subset of traffic escapes it.

# The deeper point, worth keeping

A STRICT DECODER DEFEATS PRECISELY THE FORWARD-COMPATIBILITY A VERSION FIELD EXISTS TO PROVIDE.
Adding the version did not make this envelope forward-compatible. It made the NEXT change
diagnosable. That is still worth having, but do not mistake it for tolerance.

The strict decoder is the standing posture on this surface and is NOT being changed here -- an
unknown field on a federation surface is a real signal. The cost is paid in deploy discipline.

# Two safe rollout orders -- pick one and record which

(1) READERS-FIRST, no downtime window. Ship a build that ACCEPTS the field but does not EMIT it to
    every bus. Confirm all buses are on it. Then ship the emitting build. At no point does a versioned
    frame meet a peer that cannot read it.

(2) DRAIN AND RESTART TOGETHER. Drain egress on every bus, confirm outboxes empty, restart all buses
    on the new build simultaneously. Simpler, needs a window, and needs the drain to be VERIFIED
    rather than assumed.

Order (1) is preferred for a live federation. Order (2) is acceptable for the local three-bus dev set.

# Acceptance
  - the chosen order is recorded in DECISIONS.md with its reasoning
  - a rehearsal on the local three-bus Docker set proves a message survives the rollout end to end
  - and, the case that actually matters: prove the FAILURE mode first. Stand up one upgraded and one
    un-upgraded bus, send through, and OBSERVE the 400-and-abandon. A rollout plan whose hazard was
    never reproduced is a plan nobody has tested.
  - docs/THREE-BUS-DOCKER.md updated with the rollout step
