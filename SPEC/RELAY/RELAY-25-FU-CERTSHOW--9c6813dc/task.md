## Description

To read a PUBLIC value today -- this bus's own TLS certificate fingerprint -- an operator must run `agent-bus invite mint -json` and read the `bus_cert_fingerprint` field: i.e. mint a single-use bearer credential, consuming an invite, purely to read something that is not secret. scripts/fed-smoke.sh:339-340 does exactly this and apologises for it in a comment. Wants a read-only `agent-bus cert show --json` (or equivalent) subcommand that prints the bus's own certificate fingerprint (and any other public cert metadata worth surfacing -- e.g. not-before/not-after) without consuming an invite or minting anything.

COUNTER-INTUITIVE FACT ESTABLISHED TODAY, record it in the task and in the eventual doc update: the bus uses ONE certificate in BOTH directions. internal/buscert/buscert.go:636 mints the leaf with BOTH ServerAuth and ClientAuth ExtKeyUsage, and its own comment states "this same certificate is what the bus PRESENTS when it dials a PEER bus. One identity, both directions." DECISIONS.md:4538-4541 rules this explicitly (IsCA + both EKUs, deliberate). So a single `cert show` covers BOTH the inbound-server and outbound-relay-client roles -- there is no second certificate to expose separately, today.

FORWARD RISK, note it rather than solve it here: MTLS-RELAYGUARD (8192c3c7-78cb-44a4-a841-54b72be8fc2a) may later mint a SEPARATE relay client certificate. If it does, the one-cert-both-roles assumption behind this task (and behind fed-smoke.sh's own inbound-binding comment) breaks. It fails CLOSED (an availability problem, not a security hole), but fed-smoke.sh -- and this new `cert show` command's output shape -- would need updating in the SAME change that introduces the second certificate, not discovered later. Wired a relates edge to MTLS-RELAYGUARD so that task's owner sees this dependency.
