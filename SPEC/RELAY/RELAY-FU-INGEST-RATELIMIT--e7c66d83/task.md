## Description

Filed 2026-08-14. P0 #4 of four verified independently by the security gate against the watermark task (86c7d368), previously recorded only inside that task's notes. Of the four, the coordinator's own read is that this is the one that most obviously must exist before three buses talk.

THE GAP: relayed messages ingested via hub.IngestRelayed bypass every local-agent throughput control (MaxOutstandingMints and its siblings) entirely -- there is no rate limit, no quota, and no concurrency cap on the relay ingest path of any kind. A local agent's send volume is bounded by the outstanding-mint mechanism; a peer bus's relayed volume is not bounded by anything.

COMBINES WITH RELAY-FU-IDEM-METER-BY-PEER (8774f265, raised to P0 as its own judgement call): that task closes the applied-key-table exhaustion specifically; this task is the broader missing throughput control (any resource the relay ingest path touches without a local-agent-equivalent bound -- CPU, connection/goroutine counts, whatever downstream costs a relayed message imposes beyond the idem table). Treat as related but distinct scope -- see that task's own note for the applied-key-table-specific mechanics this task should not duplicate.

SCOPE: design and wire a rate limit / quota / concurrency cap for the relay ingest surface, scoped per authenticated peer bus (the only proven identity available at that layer, per RELAY-FU-PEERBUSID-CROSSCHECK's and RELAY-FU-IDEM-METER-BY-PEER's shared framing). Candidate shape: a limiter constructed independently (matching the existing pattern where relay.NewRegistry/NewHandler/NewRosterHandler already construct cleanly from cmd/agent-bus today) that RELAY-24 then wires in alongside the acceptor, rather than logic embedded directly in RELAY-24's own composition code -- confirm this shape during implementation; it is a design read, not a settled decision.
