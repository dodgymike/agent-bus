## Description

Filed from the RELAY-24 reviewer's finding #1 (2026-08-14), previously recorded only as a doc comment and a verbal report -- reviewer explicitly noted no task existed for it and required it be filed before accepting the finding as closed. Same shape as the bus-path off-by-one the coordinator notes was just fixed at 05ad5fc (RELAY-FU-BUSPATH-OFFBYONE): a PERMANENT refusal reaching the peer as a RETRYABLE status code, so an honest peer that mis-stamped its hop cannot fix the problem by resending and retries for its whole retry horizon.

THE GAP, verified directly at cmd/agent-bus/relaywiring.go:739-748 and internal/relay/relayhttp.go: the last-hop binding refusal (the authenticated peer does not match the claimed last hop in RelayedMessage.BusPath) is returned wrapping only the wiring-private `errPeerClaimMismatch`. relayhttp.go's post-callback switch classifies only `ErrUnknownLocalRecipient` (404) and `ErrIdempotencyViolation` (409) by name and sends EVERYTHING ELSE to a 503 default (relayhttp.go:374). `PeerRefusedError.Retriable()` (client.go:56-95) reports that 503 as retriable. The two SIBLING refusals on adjacent surfaces get this right: `ErrPeerRejected` -> 403 (handshake), `ErrUnknownPeer` -> 403 (roster) -- this one is the odd one out, and relayhttp.go's own comments about permanent-vs-retryable classification (:242-244, :345-353) argue in their own words that a permanent refusal must be a final 4xx.

FIX, per the reviewer's own smallest-fix sizing: wrap the refusal in `relay.ErrPeerRejected` at relaywiring.go:747 AND add the matching `errors.Is(err, ErrPeerRejected) -> 403 CodePeerRejected` arm to relayhttp.go's post-callback switch. This is a boundary extension (a new relay sentinel reaching a 4xx from AcceptRelay specifically, not just from the handshake/roster surfaces) -- confirm the shape is still correct when this task starts, since relayhttp.go and relaywiring.go may have moved.

ALREADY PINNED BY A TEST: relaywiring_relay24_test.go:921-927 asserts the refusal matches NONE of the sentinels relayhttp classifies -- confirmed by the reviewer to go RED the day this is fixed. Extend or replace that assertion as part of this task rather than leaving it as a permanent known-gap marker.

NOTE the double-sentinel cosmetic nuance the reviewer flagged: PeerRefusedError.Retriable() makes EVERY 4xx final regardless of which one, so 403-vs-409 (if 409 were chosen instead of 403) would not change retriability -- only the diagnosis code an operator reads. Pick 403 for consistency with the two sibling refusals unless a concrete reason favours otherwise.
