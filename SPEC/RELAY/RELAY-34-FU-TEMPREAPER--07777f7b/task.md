## Description

A crash between os.CreateTemp and os.Rename in atomicReplacePeerWithdrawalFloor leaves a .peer-withdrawal-floor-* file in the data directory for ever. internal/wal/indexfloor.go HAS a reaper for its own temp pattern; internal/ids and internal/hub do not, and neither does RELAY-34's new writer.

Impact is untidiness plus unbounded inode growth under repeated crash-during-withdrawal, not a correctness bug: the temp file is never read, the real file is replaced atomically, and a reader sees the whole old file or the whole new one. Filed so the inconsistency across the four floor files is a decision rather than an oversight -- either all of them reap or none do, and the answer should be the same everywhere.

Found by the RELAY-34 security gate.
