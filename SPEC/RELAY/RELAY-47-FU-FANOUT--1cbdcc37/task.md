## Description

Filed 2026-08-15 by spec-keeper on behalf of the RELAY-47 feature-runner. Accepted residual of RELAY-47, recorded rather than silently left.

RELAY-47 shipped `maxOnwardBusesPerMessage = 8`, counted at the WIRING SITE over the distinct FOREIGN DESTINATION bus halves named in the envelope. The SOUND bound is the number of distinct **resolved NEXT HOPS** -- the addresses actually dialled -- which only `relay.Forwarder.targets` knows, because `-route-for` can collapse many destinations onto one next hop and (see RELAY-49) a destination is not the same object as a next hop at all.

**The current placement was a DELIBERATE choice, not an oversight:** counting inside the wiring site avoids creating a SECOND routing authority beside the Registry, which would be a worse defect than a slightly loose bound. Any fix must keep exactly one routing authority -- i.e. move the COUNT into the forwarder, do not replicate the ROUTING into the wiring site.

Interaction to settle at the same time: with the bound counted on destinations, the RELAY-49 bounce (split horizon applied to the destination rather than the next hop) is not constrained by it. A next-hop-based bound constrains both, so these two tasks should probably be taken together, RELAY-49 first.

== PROOF ==

    go test -race -run TestOnwardFanOutBoundCountsDistinctNextHops ./internal/relay

Cases: (a) N destinations collapsing onto ONE next hop -> counts 1, not N (must not be refused); (b) more than 8 distinct next hops -> refused at 8, with the refusal logged specifically; (c) the routing decision is still made in exactly ONE place (an AST/structural check, or the test asserts the wiring site performs no route lookup). Confirm RED before the fix.

RELATES: RELAY-47, RELAY-49.
