## Description

P2 reliability/security follow-up from RELAY-25 preflight (2026-08-14). `scripts/bus-serve.sh` records only a numeric PID and `pid_running` uses `kill -0`; after the bus exits, the kernel may reuse that PID for an unrelated process. `status` can report a misleading process state and `stop` can send SIGTERM/SIGKILL to the unrelated process, especially because stop does not re-check that the PID belongs to the bus before either signal. The existing pidfile syntax hardening and RUN_DIR ownership task do not establish process identity, and the existing wrapper test only proves the normal final stop.

DEFINITION OF DONE:
1. Bind the pidfile to a process identity available on the supported runtime (for example Linux `/proc/<pid>/stat` starttime plus an executable identity), with a versioned/strict format and fail-closed parsing. `status`, `start`, and every TERM/KILL decision must verify the identity, not only `kill -0`; a stale/reused PID is treated as not running and is never signalled.
2. Add a race-focused test using a harmless sentinel process: simulate the bus PID exiting and a different process occupying the recorded PID (or an equivalent deterministic identity mismatch), assert `stop` never signals the sentinel, removes only its own stale pidfile, and leaves the sentinel alive. Assert the SIGKILL escalation path re-checks identity after the wait as well.
3. Keep the final-stop proof non-vacuous through the compiled/server wrapper path: a real isolated `start -> status -> stop -> status` must pass, and the identity-mismatch negative must pass. Update CONTRACTS-AGENT.md and AGENT_PROTOCOL.md for the pidfile identity/refusal and unchanged exit-code semantics. Do not weaken the existing numeric PID validation or RUN_DIR ownership/symlink protections.

SECURITY NEGATIVES: never signal PID 0, -1, a process-group value, an arbitrary reused PID, or a process whose executable/starttime does not match; never treat a health probe alone as proof that the PID is ours; do not broaden cleanup to delete another run directory's pidfile. This remains nonblocking for the federation critical path and is distinct from RUN_DIR ownership/symlink hardening and the already-landed numeric pidfile validation.
