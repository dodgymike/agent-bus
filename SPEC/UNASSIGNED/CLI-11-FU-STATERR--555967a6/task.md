## Description

Follow-up to CLI-11 (bf966c07-5f99-4fe6-bb23-52868ed04c33), reviewer P2.

checkBusIdentityPresent (cmd/agent-bus/invite.go:664) treats ANY os.Stat error as "the file is absent". On EACCES or EIO -- the file is there, we just could not look at it -- `agent-bus invite mint` exits 4 saying the data directory holds no bus certificate and the remedy says the file has been LOST and must be RESTORED FROM BACKUP. That invites an operator to overwrite a bus certificate or a bus-id file that is present and fine, which for the bus-id file renames the bus away from its own certificate and, per invariant 2, makes every agent id it ever issued name a bus that no longer exists.

internal/buscert already refuses to make this conflation and says why (fileExists, internal/buscert/buscert.go:319-337: "a stat that fails for any reason OTHER than not there is an ERROR, never absent ... the difference between those two answers here is the difference between refusing to start and generating a new identity over the top of the old one"). The same rule belongs one level up.

FIXED ALREADY in the sibling: cmd/agent-bus/key.go checkBusKeyMaterialPresent branches on os.IsNotExist and returns exit 1 with "the file may well be present, so do NOT restore over it until you have looked" for every other stat error. This task applies the same branch to invite.go so the two commands do not disagree about what a stat error means. The reviewers note was "fix both or neither"; only the new one was fixed, because invite.go was outside CLI-11s scope.

SCOPE: the stat-error branch only. Do not otherwise change invite mints refusal behaviour, and keep TestInviteMintSubcommand green -- in particular the assertions that a refusal on a virgin data directory leaves it COMPLETELY untouched and that a lost bus-id file is REFUSED, never regenerated.
