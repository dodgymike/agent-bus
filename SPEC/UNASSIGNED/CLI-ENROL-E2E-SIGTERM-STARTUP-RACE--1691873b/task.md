## Description

cmd/agent-busctl/enrol_test.go:88 fatals with "the priming server exited badly: signal: terminated" under CPU load. DIAGNOSED, not guessed, and it is NOT flakiness-as-slowness: the test starts a priming agent-bus, calls waitForBusCertificate (which returns as soon as the certificate file appears -- written at cmd/agent-bus/main.go:491 by openBusCertMaterial), then immediately sends SIGTERM and treats ANY non-nil Wait() error as fatal. But signal.Notify for SIGINT/SIGTERM is not installed until cmd/agent-bus/main.go:1800. Between those two points sit WAL replay, hub.Open, the relay/federation wiring and httpapi.New -- roughly 1300 lines of startup. A SIGTERM delivered inside that window is handled by the Go default disposition and KILLS the process, so Wait() reports "signal: terminated" instead of a clean zero exit, and the test fatals. Under load the window widens and the race is lost.

REPRODUCED AT CLEAN HEAD 85ed77f WITH NO OTHER CHANGES PRESENT: a pristine `git archive HEAD` overlay, 16 CPU spinners on an 8-core box, `go test -count=8 -race -run TestCLIEnrolEndToEnd ./cmd/agent-busctl` -> FAIL at enrol_test.go:88 with that exact text. The same overlay unloaded passes 5/5; the ACK-5 worktree unloaded passes 5/5 and 3/3. So it is PRE-EXISTING and load-shaped, and it is a real defect rather than a slow test.

Two candidate fixes, and they are not equivalent: (a) make the TEST wait for readiness rather than for a file -- the certificate appearing does not mean the server is up, let alone that it can be signalled cleanly; (b) install the signal handler EARLY in cmd/agent-bus/main.go, before the long wiring, which is arguably right on its own merits since an operator SIGTERMing a slow-starting bus today also kills it uncleanly. (b) changes production behaviour and deserves its own judgement.

Found while determining whether an ACK-5 test failure was caused by ACK-5. It was not.
