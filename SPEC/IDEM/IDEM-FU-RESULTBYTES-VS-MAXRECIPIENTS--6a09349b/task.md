## Description

Filed 2026-08-14 from the RELAY-24-BLOCKER-HUBINGEST security gate. HIGH.

THE INCONSISTENCY: the applied-key result stores the recipient list, and idem.MaxResultBytes is 512. Local paths can NEVER hit it (Send carries one recipient, Broadcast none), but a RELAYED message may carry up to store.MaxRecipients (64). Security measured the real threshold: it FAILS AT 24 recipients with test-length ids ("515 bytes, but a stored result is at most 512"), and at roughly 13 with production-length ids. So relay.ValidateRelayRequest admits 64 while the hub refuses ~13 -- the two bounds disagree, and the hub is the tighter one.

WHAT IS IN PLACE TODAY IS A WORKAROUND, SO LABELLED IN ITS OWN DOC: hub.relayedResultFits pre-refuses these BEFORE minting a sequence. Without it the failure lands INSIDE publish after the sequence is minted, relay.Acceptor maps it to 503, and an HONEST peer retries for ever -- burning one sequence per attempt plus one seq-floor fsync per 256. Either way the message is LEGITIMATE and this bus still will not deliver it.

THE REAL FIX (internal/idem): raise MaxResultBytes with the retention-budget maths redone, OR stop storing the recipient list in the stored result. Pick one deliberately -- the budget is the reason the cap is 512.

[ADDED 2026-08-14 -- from the reviewer, and IN SCOPE for this fix, not a separate follow-up:] a permanent-refusal class belongs in the relay error mapping alongside the real fix. `internal/relay/accept.go:334-339` maps EVERYTHING that is not `ErrIdempotencyViolation` to 503 ("not now") -- so even with hub.relayedResultFits's EARLY refusal, an honest peer is still told to retry a message that can never be accepted. The early refusal only stops the sequence-burn; it does not make the 503 honest. When this task lands the (rewritten) real fix, also add a permanent-refusal error class to the relay error mapping so ErrInvalidRelayedMessage (or its post-fix equivalent, if the bound itself is removed rather than merely raised) maps to a terminal response rather than 503, and update accept.go's mapping + its test coverage accordingly.

WHEN IT LANDS: rewrite TestIngestRelayedRefusesAnAudienceItCannotRemember to assert ACCEPTANCE of a 64-recipient relayed message. That test says so in its own doc comment; it is a deliberate tripwire, not an assertion of desired behaviour.

PROOF NOTE: the stored proof_cmd names the rewritten test plus an idem-side bound test. Require proof-check.sh verdict=PASS, and confirm it is RED before the fix. If the accept.go mapping change is included, extend the proof_cmd to cover its test too.
