# The disagreement

IDEM-19 amortised the expiry-queue compaction in internal/idem and internal/ack. The fix keeps a
dead prefix in the queue between compactions, which pushes the worst-case memory past what the
1 KiB-per-record rounding assumed:

  internal/idem  ~1070 B/record  -> ~66.88 MiB   against a 64 MiB budget   (~3.50 MiB over)
  internal/ack   ~1085 B/record  -> ~67.81 MiB   against a 64 MiB budget   (~3.81 MiB over)

Both retention.go files now DOCUMENT this honestly rather than moving the constant.
CONTRACTS-HTTP.md still documents the un-overshot bound. So the contract file and the code comments
now disagree, which is the exact class the doc-truth audit spent 2026-08-16 removing.

# Why MaxRecordBytes was deliberately NOT changed

Do not "just fix the constant". It is load-bearing in four places:
  - it is pinned by test
  - it divides into MaxEntries = 65536
  - it is what hub.MaxIdempotencyEntries is DEFINED as
  - it appears in CONTRACTS-HTTP.md as a published contract

Changing it is a contract change, not a tidy-up, and the IDEM-19 agent correctly declined to make it
inside a performance task. That judgement was right and this task exists because of it.

# The decision to make

Three options; pick one and record it in DECISIONS.md:

  (a) ACCEPT the overshoot and correct CONTRACTS-HTTP.md to state the real bound. Cheapest, honest,
      and treats ~4 MiB on a 64 MiB budget as within tolerance. Requires saying so explicitly rather
      than quietly restating the number.
  (b) TIGHTEN the compaction threshold so the dead prefix cannot grow far enough to overshoot. Keeps
      the published bound true at some cost to the amortisation constant. Measure the new constant --
      do not assume it stays linear.
  (c) LOWER MaxEntries so the product fits 64 MiB. Changes a published capacity, so it needs the
      same scrutiny as (a) plus a check on every consumer of hub.MaxIdempotencyEntries.

# Standard of evidence

Whichever is chosen, the bound must be MEASURED, not derived on paper. IDEM-19's guards already
observe real allocation (they were RED at 1,910,461,536 bytes against a 33,554,432 bound before the
fix), so extend those rather than writing new arithmetic.

If (a): the proof must PIN the specific line in CONTRACTS-HTTP.md and be observed RED before the
edit. A grep proof passing on an incidental match elsewhere in the file has already green-lit a bad
close in this repo.
