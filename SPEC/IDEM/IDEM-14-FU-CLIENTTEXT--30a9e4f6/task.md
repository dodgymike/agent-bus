## Description

Field evidence (2026-08-07) from a real external agent that hit idempotency-key reuse with a
different payload during tonight's plaintext->TLS migration.

The client (client/messages.go:1175) prints, as the Remedy on the 409 rejection:

  "use a FRESH idempotency key for new content -- reusing one with different content is a protocol
  violation and the bus disconnects the client (invariant 10); to RETRY the original message, resend
  it byte for byte under the same key"

MEASURED: it does NOT disconnect. The reporter watched the long-lived process across the violation:
same pid before and after, zero new stderr lines, an `agents` call immediately after returns exit 0,
and a `send` call immediately after returns `ok=true, seq=515`. Not disconnected in any observable
sense.

The refusal ITSELF is correct -- 409, and the message correctly names the violation, the invariant,
the remedy for new content, and the remedy for a genuine retry. Only the disconnect claim is false.
Per the reporter's framing: "an agent reading that text will believe its connection is gone and may
take destructive recovery it does not need (re-enrol, rebuild identity, restart supervisors).
Over-claiming a consequence is its own defect even when the refusal is correct."

Root cause, as best determined from the backlog: IDEM-14 ("Idempotency violation path -- key reuse
with a different payload rejects, logs as security, and disconnects", public_id
b0facce9-ddc0-40f2-86f3-cc2c2bb76a79) is STILL TODO -- it is the task that is supposed to define
'disconnect' concretely and implement it server-side. The 409 rejection itself is evidently already
enforced (elsewhere / earlier than IDEM-14), but client/messages.go's Remedy text was written ahead
of IDEM-14 landing and asserts a consequence the server does not yet produce. Whether the eventual
fix is "implement the disconnect" or "the disconnect never happens by design, so stop claiming it" is
exactly the decision IDEM-14's own task text says it must pin down (blast radius: drop-connection vs
full credential revocation, or neither) -- this note is field confirmation that, as of tonight, NEITHER
happens, and the client should not claim one does until IDEM-14 makes a choice and ships it.

Scope for this follow-up: fix client/messages.go's Remedy text now (stop asserting an unverified/
unimplemented consequence) OR gate the wording on IDEM-14 shipping, whichever the implementer judges
lower-risk; do not conflate this with IDEM-14's own scope of deciding+implementing the disconnect
mechanics -- cross-reference it, do not duplicate it. Rated P1 per the finding: a false claim of
disconnection can trigger unnecessary destructive recovery action by a well-behaved agent.
